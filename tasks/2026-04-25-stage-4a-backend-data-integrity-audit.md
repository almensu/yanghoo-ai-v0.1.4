# 阶段 4A：后端数据一致性审计 (Backend Data Integrity Audit)

你是 glm。前端已达到零告警状态，现在进入后端审计阶段。本阶段的目标是检查 `backend/data/` 目录下的物理文件与 `metadata.json` 之间的一致性，识别并报告所有“孤立”文件夹或“失效”记录。

## 背景

在 v0.2.0 开发过程中，可能存在手动删除文件夹、迁移脚本运行失败或任务中断的情况。
我们需要对数据层进行一次全面的“体检”，为后续的数据清理或自动修复提供依据。

## 目标

1.  **元数据 vs 文件夹**：找出 `metadata.json` 中记录但磁盘文件夹缺失的任务。
2.  **文件夹 vs 元数据**：找出磁盘上有文件夹但在 `metadata.json` 中无记录的任务（即孤立任务）。
3.  **路径验证**：对于有效任务，检查其元数据中定义的关键文件路径（`media_files`, `vtt_files`, `thumbnail_path`）是否真实存在。
4.  **输出审计报告**：列出所有不一致项，不进行物理修改。

## 强制约束

1.  **只读审计**：本阶段禁止删除任何文件或修改 `metadata.json`。
2.  **不要执行 commit/push**。
3.  **使用 Python 脚本或交互式代码**：建议在 `backend/` 环境下运行审计逻辑。

## 执行步骤

### Step 1 - 准备审计环境
- 确认 `backend/data/metadata.json` 的位置。
- 确认 `backend/data/` 目录下任务文件夹的命名规则（通常为 UUID）。

### Step 2 - 执行双向检查
编写并运行一个临时的 Python 脚本（或利用现有脚本）完成以下逻辑：
- 加载 `metadata.json` 为字典。
- 获取 `backend/data/` 下的所有子目录列表（排除 `.cache` 等系统目录）。
- **检查项 A**：遍历 `metadata.json`，标记所有对应文件夹不存在的 UUID。
- **检查项 B**：遍历磁盘目录，标记所有未出现在 `metadata.json` 中的文件夹。

### Step 3 - 执行文件路径有效性检查
- 针对 `metadata.json` 中的每个任务，提取以下字段：
    - `media_files` (可能是字符串或对象)
    - `vtt_files` (字典)
    - `thumbnail_path`
- 验证这些相对路径（相对于任务文件夹）对应的文件是否真的存在于磁盘上。
- 特别注意路径中是否存在 `../` 或绝对路径导致的潜在逻辑错误。

### Step 4 - 输出结果
将审计发现的问题记录到报告中。

## 报告要求
将报告写入：`tasks/reports/2026-04-25-stage-4a-backend-data-integrity-audit-report.md`。
报告需包含：
- **统计信息**：任务总数、物理文件夹总数。
- **孤立任务清单**：有文件夹无记录的任务列表。
- **失效记录清单**：有记录无文件夹的任务列表。
- **断链文件清单**：记录中引用的文件在磁盘上缺失的明细。
- **改进建议**：是否需要运行 `restore_orphaned_tasks.py` 或手动清理。

## 最终回复主控
完成后回复：

- 报告路径。
- `git status --short`。
